# Build guide

Use this as an execution checklist. Record each material change and do not skip acceptance tests.

## Phase 0 — Host preparation

1. Run PowerShell as a normal user and execute:

   ```powershell
   Set-ExecutionPolicy -Scope Process Bypass
   .\scripts\windows\Test-LabReadiness.ps1
   ```

2. Confirm hardware virtualization is enabled, the recommended profile fits, and disk encryption/host updates are current.
3. Install the current stable VirtualBox release from the vendor site.
4. Download operating-system images only from official vendor sites. Verify published hashes where available.
5. Create an encrypted password-manager entry for lab credentials. Do not place credentials in this repository.
6. If using the storage-saver profile, set the VirtualBox machine folder outside OneDrive, choose dynamically allocated VDI disks, and record a 20 GB free-space stop threshold.

**Acceptance:** readiness output is saved privately; all images have source URL, version, download date, and checksum recorded in `templates/asset-register.md`.

## Phase 1 — OPNsense and isolated networks

Create `fw01` with four adapters in this exact order:

1. Adapter 1: NAT (WAN)
2. Adapter 2: Internal Network `LAB-LAN`
3. Adapter 3: Internal Network `LAB-DMZ`
4. Adapter 4: Internal Network `LAB-ATTACK`

Install OPNsense from the DVD ISO, assign interfaces at the console, and configure the address plan in `01-architecture.md`. Change the default password immediately. Disable administration from WAN and keep inbound WAN rules empty. In a virtual deployment, follow the vendor guidance for hardware offloading.

Create outbound internet rules for updates. Start with deny-by-default inter-zone policy; add management and telemetry flows only as needed. Enable firewall logging on deny rules.

**Acceptance:** each zone receives its expected gateway; a test VM can update through OPNsense; no lab VM obtains a physical home-LAN address; inter-zone traffic fails until explicitly allowed.

## Phase 2 — Wazuh server

1. Create `siem01` on `LAB-LAN` and install the currently supported Ubuntu Server LTS version.
2. Set static address `10.10.10.10/24`, gateway `10.10.10.1`, and a unique hostname.
3. Apply OS updates, enable time synchronization, and take snapshot `siem01-clean-os`.
4. Follow Wazuh's current all-in-one quickstart. Save generated administrator credentials in the password manager.
5. Restrict dashboard access to the admin endpoint with an OPNsense rule.
6. Record installed versions and take snapshot `siem01-wazuh-baseline`.
7. For the storage-saver profile, configure and document a short alert-index retention period, then record disk use before and after a test day.

**Acceptance:** dashboard loads over HTTPS from the admin endpoint; system time is correct; Wazuh services survive a reboot; access from non-management zones is blocked.

## Phase 3 — Windows endpoint

1. Create `win11-01` on `LAB-LAN` using an official evaluation image and complete updates.
2. Use a non-identifying local username. Keep the built-in firewall and anti-malware controls enabled.
3. Set or reserve `10.10.10.20`, verify DNS/time, and take snapshot `win11-clean`.
4. Install the Wazuh agent using the command generated by the dashboard for the current release.
5. Install Sysmon from Microsoft Sysinternals with a documented configuration; do not blindly trust third-party configs.
6. Verify Security and Sysmon event channels are collected, then take snapshot `win11-telemetry`.

**Acceptance:** the agent is active in Wazuh; a failed local logon and a harmless process launch appear in telemetry; the endpoint still blocks unsolicited inbound connections.

## Phase 4 — Ubuntu target

1. Create `ubuntu-01` on `LAB-DMZ`; set `10.10.20.10/24` and gateway `10.10.20.1`.
2. Apply updates, enable the host firewall, allow SSH only from the admin endpoint, and install the Wazuh agent.
3. Install a simple web service only when an exercise requires it. Do not intentionally weaken the server globally.
4. Enable authentication, service, and file-integrity telemetry for a small test directory.

**Acceptance:** the Wazuh agent is active; SSH is blocked from Kali until a temporary exercise rule is approved; an edit in the monitored directory creates an event.

## Phase 5 — Kali simulation workstation

1. Create `kali-01` on `LAB-ATTACK` and set `10.10.30.10/24`.
2. Update it, create a non-root daily account, and take a clean snapshot.
3. Confirm the default rule blocks access to LAB-LAN and LAB-DMZ.
4. For each exercise, create the narrowest temporary firewall rule, test, collect evidence, then remove the rule.

**Acceptance:** Kali cannot reach the host's physical LAN, OPNsense management, or non-approved targets; approved traffic is logged; removing the temporary rule restores isolation.

## Phase 6 — Baseline and recovery

1. Export the OPNsense configuration without secrets where possible and keep the raw export outside Git.
2. Record VM settings, checksums, installed versions, and snapshot names.
3. Shut down one endpoint, restore its clean snapshot, and re-enroll/revalidate monitoring.
4. Run `scripts/windows/Test-Repository.ps1` before the first commit.

**Acceptance:** a second person could rebuild the topology from the documentation; the restore test is documented; no sensitive value is committed.
